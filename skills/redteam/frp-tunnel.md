# 长期隧道（挂得久，风险也最高）

长期通道的价值是**稳定**：自动重连、多路复用、TLS 伪装。代价是**挂得越久越容易被发现**。
所以它只在两种情形下值得用：需要给用户一个能直接用的地址，或者这条路径后面还要反复用。

## 判据：什么时候用长期隧道，什么时候用轻的

| 情形 | 选择 |
|---|---|
| 只需要几分钟把内网扫一遍 | 轻量隧道（技能 `suo5-tunnel` / `chisel-tunnel`），用完就断 |
| 要给用户一个能直接连的 socks 或端口地址 | 长期隧道（本技能），并写清地址与凭据 |
| 需要跨多天反复进入这套内网 | 长期隧道，但必须有心跳与断线重连 |
| 出网只放行 Web 端口 | 走 Web/加密通道的形态 |
| 目标完全不出网 | 长期隧道不可用，改用正向转发 |

## 判据：通道健不健康

| 观察 | 含义 | 动作 |
|---|---|---|
| 客户端显示注册成功、映射端口可访问 | 通道成立 | 实测一个内网目标再登记 |
| 客户端偶尔掉线又自己回来 | 有超时重置，自动重连在工作 | 正常，不要手动重启 |
| 反复断、再也不回来 | 出口被限或被拦长连接 | 换协议或换端口，不要在同一条路上反复重试 |
| 公网服务端端口被陌生连接试探 | 你的服务端被别人扫到了 | 立刻上认证 token，或换端口 |
| 隧道流量在目标侧出现规律性特征 | 可能被流量分析识别 | 改协议形态，或缩短使用时间 |

**最容易犯的错**：把服务端暴露在公网却不加认证。公网上的隧道服务端端口会被全网扫，
没 token 等于把内网入口送人。

## 出网受限时怎么改

顺序是：**换端口 → 换传输协议 → 换隧道方案**。前两步只改配置，第三步要重新推二进制。
不要一上来就换方案——大部分限制是端口级的，不是协议级的。

## 验证与登记

1. 从映射出来的地址访问一个**已知可达**的内网目标，拿到真实响应才算成立；
2. 可达网段必须**实测**，不要按扫描范围写；
3. 登记时说清目标侧那一端：目标出网连你的服务端（算突破）、经目标 WebShell（算突破）、
   经目标已控进程（算突破）、只在自己服务器上开代理（**不算**）；
4. 通道关闭时要同步标记为不可用，不要留一条"看着在跑其实不通"的记录。

## 纪律
- 服务端必须加认证，token 每次演练新生成，不复用；
- 目标侧的二进制与配置放临时目录，用完清理；
- 拿到核心系统后就该收尾，**别让长期通道成为唯一还在线的痕迹**。
