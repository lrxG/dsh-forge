# 白盒攻击面建模（先画图，再谈漏洞）

代码审计最常见的失败不是漏看某个函数，是**入口没列全就开始读实现**。
读完二十个 Controller 才发现真正危险的是定时任务和一个内部 RPC，判断全白做。

顺序固定：入口 → 谁能到 → 校验在哪 → 才轮到 sink（sink 交给 `audit-sink-flow`）。

## 第一步：入口只有六类，别只找 Controller

| 入口 | 在哪找 | 常被漏掉的地方 |
|---|---|---|
| HTTP 接口 | 路由表、注解、路由框架的注册文件 | 动态注册、插件式路由、版本前缀外的老接口 |
| 管理/内部接口 | 另一个端口、另一个路由前缀、独立模块 | 只在生产开放、只在测试环境注释掉但代码还在 |
| 定时任务 / 队列消费者 | 调度配置、消息监听、事件订阅 | 参数来自消息体，没有任何鉴权 |
| 文件与命令行入口 | CLI、脚本、导入导出、批处理 | 参数来自文件名或目录内容 |
| 上游服务调用 | 网关、BFF、内部 RPC 客户端 | 认为"内网调用天然可信"，把校验推给上游 |
| 前端直连 | 前端代码里写死的 URL 与第三方 SDK 的 endpoint | 只在客户端校验、直接调存储或云函数 |

产出是**一张清单**：入口标识、方法、路径/触发方式、参数来源、是否对外。

## 第二步：谁能到——三件事必须分别判断

1. **认证**：需要登录吗？登录态怎么带（cookie/header/token）？有没有匿名白名单、健康检查、静态资源前缀？
2. **授权**：谁允许调？角色、部门、租户、所有者。这一步最常出现"有认证没授权"。
3. **对象归属**：参数里传的 id 属于谁，服务端有没有再判一次归属——白盒里这是最容易确认、也最容易漏的一类。

**判据**：任意一个入口，只要"认证 / 授权 / 归属"里有一项在代码里找不到对应判断，它就是候选；
找不到不等于没有（可能在拦截器、注解、网关规则里），**必须顺着调用链找到那行判断**，找不到才算。

## 第三步：校验在哪儿被跳过

常见形状，全部按"是否真在这个入口生效"判：

- 只在网关/前置服务校验，被绕过的路径（内部调用、直连端口、代理转发）不做二次校验；
- 注解/装饰器式鉴权漏配：新增接口忘了加，或匹配规则是前缀通配，`/api/public` 把 `/api/public-admin` 一起放行；
- 只在 Controller 层判，Service 层可以被其他入口（队列、定时任务、内部 RPC）直接调用；
- 多租户靠前端传 `tenantId`，服务端只用它查库不校验归属；
- 开关/灰度把校验包在 `if (enabled)` 里，默认关。

## 交付物：一张矩阵，不是一段感受

| 入口 | 认证 | 授权 | 归属校验 | 校验位置 | 结论 |
|---|---|---|---|---|---|
| `POST /api/order/{id}/refund` | 需登录 | 无 | 无 | — | 候选：任意登录用户可退他人订单 |
| `GET /admin/users` | 无 | 无 | — | 网关 IP 白名单 | 候选：内网可达即可读 |

矩阵之外只写"待确认项"：例如"鉴权在网关注入、源码里看不到，需要在部署侧确认"。
**不要用"应该会有校验"填表**——那等于没审。

## 换路条件

- 所有入口都过同一个鉴权中间件、且有覆盖测试证明 → 这一层结束，转对象归属与内部调用；
- 入口清单来自路由框架的自动扫描，动态注册的找不到 → 换运行时抓接口（黑盒 + `control-matrix`）；
- 代码是编译产物或混淆过的 → 先转逆向（`crack` 模式），不要硬读；
- 项目过大（数十万行）→ 按入口面切片，一个模块一轮，不要通读。

## 与黑盒技能的分工

`object-and-tenant` / `control-matrix` 是黑盒视角：用探针判"这个接口有没有闸"。
本篇是白盒视角：**把入口列全、把闸的位置找出来**。两边结论要能对上——白盒说"有归属校验"，
黑盒换 id 仍能读到，说明那行校验没生效，这种矛盾本身就是线索。

## 落库

每个候选入口落一条（漏洞或资产状态），证据写**文件与行 + 调用链**，不要只写"缺少鉴权"。
矩阵本身作为靶标资产的一部分，收口时用它回答"还剩哪些入口没看"。
