# 命令执行场景下的隧道（没有 WebShell 怎么进内网）

## 与 WebShell 隧道的分工

| 入口形态 | 用什么 |
|---|---|
| 有 WebShell（能上传文件、能 HTTP 交互） | Web 隧道（技能 `suo5-tunnel`），最不显眼 |
| 只有命令执行（RCE、注入、模板执行） | 本技能：把二进制推上去跑客户端 |
| 需要长期稳定、还要给用户一个能直接用的地址 | 长期隧道形态（技能 `frp-tunnel`） |
| 只需要把一个端口临时转出来 | 本技能的反向端口转发即可，不必建 SOCKS |

## 判据：这条路通不通

| 观察 | 含义 | 动作 |
|---|---|---|
| 目标能主动连到你的公网地址 | 目标出网正常，反向隧道可行 | 建反向隧道 |
| 目标只能出 80/443 | 出网被限制在 Web 端口 | 改隧道协议走 Web 通道 |
| 目标完全不出网，但你连得进去 | 必须用正向隧道（你在目标上起服务端） | 换方向 |
| 二进制推上去跑不起来 | 架构不匹配或缺依赖 | 换对应架构的静态二进制，不要反复试 |
| 连上了但流量走不动 | 目标侧限速或中间设备在拦长连接 | 降并发、改协议，或换隧道类型 |
| 跑一段时间就断 | 有超时或代理重置 | 加自动重连，不要手动重连十次 |

**关键判断**：先确认"目标能不能出网、出哪个端口"，再决定隧道方向与协议。
方向选错，后面所有参数调整都是白费。

## 目标侧与本机的区别

目标侧跑的是**目标系统的二进制**，本机跑的是**本机系统的二进制**，两者架构几乎总是不同。
把本机那份推到 Linux 靶机上一定跑不起来——这不是配置问题，是推错了文件。

命令的写法也要跟着变：在目标侧执行的是目标 shell 的语法，在本机执行的是本机 shell 的语法。
判断依据是"这条命令在哪台机器上跑"，不是"这段文字属于哪个平台的技能"。

## 隧道建立后必须验证

1. 从隧道里访问一个**已知可达**的内网目标，拿到真实响应；
2. 记录**实测**可达网段，不要按扫描范围猜；
3. 降并发试跑一小批，确认稳定后再放开；
4. 登记时必须说清目标侧那一端（目标出网连接 / 经目标 WebShell / 经目标已控进程），
   只在自己服务器上开代理不算突破。

## 清理
目标侧的二进制与配置文件放临时目录，用完删除；服务端用完关掉，
不要留一个还开着的公网代理——那既是资源占用也是痕迹。
