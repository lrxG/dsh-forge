# 首次使用引导（判断缺口，而不是念清单）

**核心原则**：一次把话说完、一次要齐。挤牙膏式反复找用户要东西，是这个技能唯一要避免的失败。

**红线**：工具只放在 `$DSH_HOME/tools` 或用户配置的目录；模型可下载到 `$DSH_HOME/tools` 后 `toolbox sync`，不要把工具写进系统目录或项目工作目录。FOFA_KEY / VPS 这类凭据仍由用户提供。
工具路径一律以预检返回的解析结果为准。

## 判据：什么算"配好了"

| 信号 | 含义 |
|---|---|
| 预检里每个需要的工具都能解析出路径 | 工具层就绪 |
| FOFA_KEY 自测返回有效 | 测绘能力可用 |
| 能 SSH 到落地端并执行一条命令 | 反弹与中转能力可用 |
| 技能列表里没有"缺环境变量/占位符没填"的项 | 技能层就绪 |

**四项齐了才算就绪。** 只看"文件存在"不算——工具在盘上但跑不起来，和没有一样。

## 缺口会降级成什么样（要如实告诉用户）

| 缺什么 | 还能做什么 | 会失去什么 |
|---|---|---|
| 测绘 key | 证书透明 + 被动 DNS + 子域枚举 + 搜索引擎 | 资产收集不完整，**未备案与边缘资产会漏** |
| 落地端（公网服务器） | 只做不需要落地的成果：账号权限、数据、未授权访问、WebShell 交付 | **拿不到服务器权限、进不了内网**，边界与内网类得分基本放弃 |
| 扫描与漏洞检测工具 | 用已配置的替代品 | 漏洞发现能力大幅下降，Nday 检测基本瘫痪 |
| 全部都缺 | 只做纯被动信息收集与资产梳理 | 明确说清"这次只能到信息收集阶段" |

**判断规则**：缺口影响的是"能打到多深"，不是"能不能开工"。
用户明确说"就按现有条件打"时才降级开工，并在结论里写清哪部分能力被降级了。

## 怎么要（一次要清）

每一项都要说三件事：**要什么、为什么需要、给到哪**。
不要只说"缺 FOFA_KEY"，要说清没有它会漏掉什么——用户才能判断值不值得给。

## 配完必须实测

1. 测绘 key：发一次最小查询，看返回是否有效；
2. 落地端：登上去执行一条命令；
3. 工具：让预检重新解析一遍，确认每个需要解析的工具都拿到了路径；
4. 全部通过后跑一次预检；插件会自动写首次体检标记，下一次 `onboarding.first_run` 变 false。全部可用时 `onboarding.complete=true`。

改过环境变量后**必须重启宿主**才在新进程里生效——这一步要明确告诉用户，我不能替他重启。

## 单独重配某一项时

用户后面单独补一个工具或一个 key 时，不要重走全套引导：
只验证那一项、只复核受影响的能力，其余不动。重复走全套引导会让用户觉得在走流程。
