# 手工还是上工具（工具是手段，不是目标）

工具只是加速器，**目的一直是那个结论**：这个点成不成立、能不能利用、能拿到什么。
目的清楚再选手段；目的没达成就先判断是工具的问题还是目标的问题，别硬着头皮磨同一个工具。

## 什么时候手工、什么时候上工具

看这次任务做到哪一步，不看手上有哪个工具：

| 这次要做到 | 手段 | 停在哪 |
|---|---|---|
| 证明存在 | 手工发一次，拿到一个可控回显 | 有回显就停，不要顺手跑全套 |
| 证明可利用 / 拿数据 | 上工具跑一次（注入、爆破、反序列化链） | 拿到数据或明确失败就停 |
| 持续利用 / 批量 | 工具常驻，输出落文件 | 只把结论带回对话 |

两条补充判据：

- **手工预计要 2–3 轮以上才能确认**（盲注、时间型、布尔、编码绕过）→ 直接上工具。
- **先手工把点和参数定位准，再把已确认的点交给工具**。让工具从零开始扫一大片，token 和噪声两头亏。

一句话：**找洞靠手工，打洞靠工具，铺面靠工具，取证靠手工。**

## 工具挂了：先归因，别硬试

失败只有三种，处理方式完全不同：

| 归因 | 表现 | 怎么办 |
|---|---|---|
| 环境 | 找不到程序、起不来、缺依赖、代理不通、权限不足 | 当成环境事实报一次，换等价手段或问用户；**不要重复同一条命令** |
| 用法 | 参数写错、第一次用这个工具、回包在提示用法 | 看回包修正**一次**；第二次仍错就换路，不要猜参数 |
| 目标 | 工具正常跑完，但没有结果 / 被拦 / 全是同一句拒绝 | 这是目标侧的结论，不是工具坏了；换方法或放弃这一处 |

**两次原则**：同一工具、同一目标，连续两次失败就换路——换等价工具、换手工验证、或换下一个目标。
第三次尝试要有新信息（新参数来源、新入口），否则只是重复消耗。

**工具跑通但没结果 ≠ 漏洞不存在**：只能说明这个工具、这个参数集没打到。要不要换方法，看这次任务还需要不需要这个结论。

## 工具不可用时的降级路线

缺什么以体检结果为准，不要猜路径；缺了就走降级，不要停在"等工具装好"：

| 缺 | 手工替代 |
|---|---|
| 注入工具 | 手工构造几个对照 payload 判布尔/时间差，只验到"存在"这一层 |
| 模板扫描器 | 手工核对指纹与版本，公开 PoC 手工复现一次 |
| 目录爆破 | 按业务语义猜路径（接口文档、前端 chunk、备份命名） |
| 爆破/哈希工具 | 只做少量默认口令尝试，记下"需要离线爆破"作为卡点 |
| 隧道工具 | 先确认出网与可达性，不可达就如实回报，不要反复换协议 |

**降级不等于降标准**：结论仍然要能复现，只是换了取证方式；采不到的证据写进卡点，不要写成成果。

## 换路条件

- 同一工具同一目标两次失败 → 换路；
- 工具报环境错误 → 记环境事实，走降级表；
- 工具跑通无结果，且任务不再需要这个结论 → 收口，不再试；
- 手工已经能证明存在、任务也只要求到这一步 → 不要为了"更完整"再上工具。

## 落库

工具失败写进卡点与环境事实，**不要写进漏洞**；降级取证得到的结论同样要带证据（原始请求 + 回显）。
同一处试过哪些工具、各自为什么失败，写一行就够——这比再试第四次有用。
