# Web 指纹（判断打到哪一层）

## 判据：什么才算"识别出来了"

| 证据 | 可信度 | 说明 |
|---|---|---|
| 报错页/异常堆栈里出现产品名与版本 | 高 | 最硬的证据，版本号可直接拿去查 CVE |
| 特征路径存在（`/actuator`、`/solr/admin`、`/nacos/`、`/druid/index.html`） | 高 | 路径本身就是产品指纹，比页面标题可靠 |
| 静态资源路径与文件名规律（`/static/js/app.<hash>.js`、`/_next/static/`） | 中 | 能定框架大类，定不了精确版本 |
| Cookie 名与结构（`JSESSIONID`、`PHPSESSID`、`ASP.NET_SessionId`、`rememberMe`） | 中 | 定运行环境；`rememberMe` 直接指向 Shiro |
| 响应头 `Server` / `X-Powered-By` | 低 | 常见被改或剥掉，只能作参考 |
| 页面标题与 favicon 哈希 | 低-中 | 适合批量筛"哪些是同一套系统"，不适合定版本 |

**只有到"版本可确认"这一档，才值得直接去查这个版本的已知漏洞**。停在"是个 Java 应用"这种程度的，
继续往下查 CVE 是浪费时间——应该转去看暴露面（未授权接口、管理端、文件上传点）。

## 判断顺序

1. **先看有没有暴露面**，再看是什么产品。一个开着 `/actuator/env` 的 Spring 应用，
   比一个 CVE 一堆但版本不明的系统更值得先动手；
2. **同 IP 多站点**是常态（vhost），指纹要按 Host 分别取，别拿主站结论套所有子域；
3. **指纹冲突**（`Server: nginx` 但报错是 Tomcat 堆栈）说明前面有反代，**漏洞要打在反代后面的应用层**；
4. 批量场景先用最短路径筛出"值得细看"的一批，再对这批做深度指纹——不要一上来对每个站点跑全量探测。

## 换路条件

- 同一资产三种手段（路径特征、报错、静态资源）给不出一致结论 → 说明在 CDN/WAF 后面，
  直接针对报错与暴露面走，不要再堆指纹手段；
- 指纹能定产品但定不到版本，且没有暴露面 → 这个站点先放低优先，去做别的资产；
- 站点对探测请求返回统一 200 假页面（软 200）→ 所有基于状态码的判断全部失效，改用响应体差异判断。

## 执行位置
本机。探测请求走代理或按目标策略，不要用本机直连。

## 落库
每个资产的指纹记一行：产品、版本（有就写，没有就留空而不是猜）、证据原文（报错片段或特征路径）。
版本是猜的就不写，**写错的版本会让后面照着打不存在的洞**。
