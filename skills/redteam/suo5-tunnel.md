# WebShell 内网隧道（判断通不通）

拿到 WebShell 只是入口，**能把内网流量稳定代理出来才算突破**。隧道的价值不在建起来，
在于**能证明它真的通**。

## 判据：隧道算不算成立

| 观察 | 结论 | 动作 |
|---|---|---|
| 隧道进程起来了、客户端也连上了 | **还不算** | 必须从隧道里访问一个内网目标拿到真实响应 |
| 能从隧道里 curl 到内网某主机的真实页面 | 成立 | 登记隧道，标可达网段 |
| 能连上但访问任何内网目标都超时 | 隧道是通的、目标不可达 | 换目标验证，或确认这台机器到底能到哪些网段 |
| 每隔一段时间断一次 | 目标侧有超时或代理重置 | 加自动重连，降低并发 |
| 隧道建立后 WebShell 本身不可访问了 | 入口被隧道打挂了 | 立刻停，先恢复入口，再换更轻的用法 |

**最关键的判断**：不要在隧道刚建好时就大批量扫描。先发几个包确认稳定，
再决定并发上限——很多"内网没东西"其实是隧道拥塞。

## 什么时候换隧道类型

| 情形 | 换什么 |
|---|---|
| 有 WebShell，HTTP 通道可用 | 保持 Web 隧道（流量藏在正常请求里，最不显眼） |
| 只有命令执行，没有 WebShell | 换成基于二进制的隧道（技能 `chisel-tunnel` / `frp-tunnel`） |
| 需要长期稳定、还要给用户直接用的地址 | 换成长期隧道形态（技能 `frp-tunnel`） |
| 隧道一跑就把目标资源吃满 | 降并发、限制同时连接数，不要换方案硬扛 |
| 目标出网只放行特定端口 | 把隧道入口改成对应端口，或改协议类型 |

## 目标侧那一端必须说清楚

登记隧道时最容易犯的错是**把"我在自己服务器上开了个代理"当成突破**。区别在于：
- 目标主动连出来（目标上跑客户端）→ 算突破；
- 经目标 WebShell 转发 → 算突破；
- 经目标上已控进程转发 → 算突破；
- **只在自己服务器上开代理 → 不算**，因为目标的网络边界根本没被跨过。

这一点决定了后面所有"边界"类得分是否成立，判断错了整份报告都站不住。

## 隧道里的扫描节奏

1. 先单点验证，再放并发；
2. 隧道只代理 TCP，UDP 类协议（Kerberos、部分反连）要走端口映射；
3. 每扩一层（从 A 主机摸到 B 网段），都要重新登记可达范围，**别猜**；
4. 隧道掉了要立刻标记为不可用，不要留一个"看起来在跑其实不通"的隧道给后面的动作踩空。

## 纪律
- 进内网前先建隧道。
- 隧道入口的 WebShell 要是加密马，否则用户无法复用；
- 用完清理目标侧的落地文件，恢复原状。
