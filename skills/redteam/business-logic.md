# 业务逻辑与竞态（规则被绕过，而不是被攻破）

这两类没有 payload，判断全靠一件事：**服务端接受了一个本不该接受的结果，并且这个结果能被我观测到**。
观测点只有三个：余额/额度变了、单据/订单状态变了、库存/计数变了。界面上显示成功不算。

## 先找规则，再找绕过点

把业务拆成三样东西再动手：

1. **上限**：次数、金额、库存、时长、人数、文件大小——上限存在哪一层（前端校验/接口校验/账务核对）。
2. **状态机**：允许哪些转移，哪些转移应该被禁止（未支付→已发货、已退款→再退款、试用→正式）。
3. **归属**：这个对象属于谁，操作时服务端有没有再判一次（与 `object-and-tenant` 交叉）。

**判据**：我做了一次不该成功的动作，服务端接受了。回包里"操作成功"不算，要看流水/列表/余额。

## 常见绕过形状

| 形状 | 判据 | 反例 |
|---|---|---|
| 次数/额度 | 同一凭证超出上限仍成功，且计数真的超了 | 只在前端置灰 |
| 金额与数量 | 负数、小数、超大值、单位不一致（分/元）被接受，账务按错值结算 | 接口拒绝、只是显示异常 |
| 优惠叠加 | 同类券/活动重复生效，或互斥规则只在提交时校验一次 | 只在一个页面显示两张券 |
| 状态机跳步 | 直接调到后面状态（跳过支付/审核），且落库生效 | 前端隐藏按钮 |
| 退款/提现 | 可重复退、可超退、退款后订单仍可用 | 只是提示错误 |
| 试用/邀请 | 换标识重置资格，或邀请关系可自指 | 需人工审核 |
| 幂等键 | 去掉幂等键或换一个就重复入账 | 服务端按内容去重 |

## 竞态：只认"并发下与串行不一致"

- 做法是**同一动作并发多次**（同一账号、同一对象、同一时刻），看最终状态是否超出业务上限。
- **判据**：并发 N 次后，余额为负、券用到超过张数、库存卖超、积分重复入账——任一条成立且可复现。
- **不算**：并发下报错、部分失败、界面卡顿；那只是没做好并发控制，不是业务损失。
- 要记录**并发度与复现次数**，一次成功不算，重复三次以上才算成立。
- 分布式场景要区分"最终一致"与"永久不一致"：过一段时间自己对账回来的，不算漏洞。

## 判据来源（哪份数据说了算）

服务端流水/账单 > 数据库落库结果 > 接口返回结构 > 界面显示。
界面与流水冲突时以流水为准；接口说成功但流水没记，按"未成立"处理，反过来才是漏洞。

## 换路条件

- 所有入口都做了服务端重算与上限校验 → 这个面封死，转对象面或并发面；
- 并发下结果一致、无超额 → 该接口不是竞争点；
- 只能在前端绕过（改 DOM、跳过步骤但服务端拒绝）→ 记为"前端校验缺失"，不写成业务漏洞；
- 需要人工审核才生效 → 记线索，不算成果。

## 落库

每条写清：**规则是什么 → 我怎么绕的 → 结果落在哪份数据上**，附原始请求序列与前后状态截图。
竞态类必须写并发度、次数与最终余额/库存数字；金额类写清单位与结算口径。
