# 授权验证：流、点、证据

## 触发条件

- 提到卡密、授权、激活、试用、注册机、patch；给了 EXE/APK/源码/activation 请求包
- CTF crackme、授权系统审计

## 这件事的结构

授权不是一处判断，是**一条流**，改错一环会被下一环打回：

1. **入口**：登录、激活、启动校验、功能内二次校验，各自独立。
2. **比较点**：签名、设备绑定、时间/次数、服务端返回。
3. **持久化**：注册表、文件、缓存、账号态。
4. **在线门闸**：服务端复核——本地改不动它。

先画这条流，再决定改哪里。字符串与 API 调用是**入口线索**，不是结论：命中 "Invalid License" 只说明有这句话。

**patch 点只有三类**：条件跳转、返回值、在线门闸。前两类本地生效，第三类必须动响应。

**本地 harness 的作用**是把"客户端行为"和"服务端行为"分开：能离线复现的校验是本地校验，必须联网才出现的门闸只能改响应或如实标注。

## 判据：破解算不算成立

- 三个条件缺一不可：**干净样本未授权 → 打完补丁真解锁 → 回滚后恢复未授权**。
- 反幻觉：只改了提示文案或界面显示，逻辑没变；本地解锁了但服务端二次校验仍拒；keygen 只拟合已知几组输出是查表，不是算法。
- 同一授权逻辑可能分布在启动校验、功能内二次校验、注册表/文件标记三处，只改一处会表现为"时好时坏"。
- **换路**：加固壳脱不掉、或校验在服务端 → 本地改动只能骗界面，如实标注"仅前端绕过"。

## 交付

验证流图 · patch 点位置与理由 · 本地 harness · 复现步骤 · 回滚方式（原件保留）。

- **+ pentest**：API 分析 → 在线门闸绕过
