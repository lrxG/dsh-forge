# 游戏客户端：数据源与链路

## 触发条件

- 提到外挂、ESP、透视、自瞄、trainer、修改器、内存修改
- 给了游戏进程名、APK、Unity/Unreal 相关文件

## 这件事的结构

1. **先认引擎**：Unity（libunity / Assembly-CSharp / global-metadata）、UE（libUE4 / .pak / GNames）、Cocos、自研。引擎决定 SDK 形态与数据从哪来。
2. **数据源是核心**：实体列表、对象结构、骨骼索引、血量与队伍字段的来源，比绘制代码重要得多。数据源错了，画得再漂亮也是错的。
3. **读写方式两种**：外部读写（进程外，稳定但慢）与内部注入（快、易被检测）。选哪种取决于目标与风险，不取决于习惯。
4. **坐标链路**：世界坐标 → 裁剪空间 → NDC → 屏幕。任一步错都表现为"框飘"，所以先验证链路再谈效果。
5. **反作弊决定可行性**：内核级或服务端校验存在时，本地效果不等于可用。
6. **离线优先**：先用假实体验证整条链路，再接真实目标——离线能复现的才是能力，联机上偶然成功不算。

## 判据：改对了没有

- 有效：改动后游戏行为**稳定变化**，并且重启或新开一局仍然生效——否则只是临时改了显示。
- 反幻觉：只改 UI 显示的数值，存档与服务端没变；指针链在版本更新后失效，改到的是旧地址；修改成功一次不等于地址稳定。
- 同一数值可能有多份（内存、存档、服务端），只改内存会表现为"读条后回弹"。
- **换路**：存在反作弊或服务端校验时，本地 trainer 只能骗本地，如实标注这一点，不要把本地效果当成已破解。

## 交付

引擎与数据源假设 · 结构与偏移 · 绘制或修改链路 · 可运行入口（默认用假实体，不接联机）· 限制与失效条件。

## 与其他技能配合

- **+ reverse**：引擎结构 → 数据结构恢复
- **+ exploit**：客户端脆弱点 → 利用
