# 逆向工程：理解与判据

## 触发条件

- 提到逆向、反编译、脱壳、hook；给了二进制、伪代码、汇编或崩溃栈
- 要恢复算法、重构协议、定位 patch 点

## 这件事的本质

逆向不是把工具跑一遍，是**用最少的证据回答一个问题：这段二进制凭什么做这个判断**。顺序由证据决定，不由工具决定。

1. **triage 先定性**：格式、架构、字节序、编译器、保护机制。保护决定后面所有路线的成本——先认壳，再谈分析。
2. **静态只找"做判断的地方"**：入口与初始化、校验、加密、网络通信、字符串引用、调用图。通读全部代码是浪费。
3. **动态补静态的盲区**：控制流说不清、数据来源不明、字符串被加密时，用调试器或 hook 看真实入参与返回值。
4. **去混淆先分类**：压缩壳、虚拟化、字符串加密、控制流平坦化，路线完全不同。脱不动的壳是卡点，不是耐力测试。
5. **算法恢复**：认出已知算法（AES/RSA/CRC/哈希）比硬读汇编快得多；自定义算法必须重实现，并用样本内的真实输入输出对齐。
6. **补丁改判断点**，不改文案；改完验证行为差异只出现在该功能上。
7. **协议靠多条同类消息对齐**出字段与状态机，不靠单条样本猜。

工具按平台选，路径取本机实际安装：静态 IDA / Ghidra / r2 / Binary Ninja / dnSpy；动态 x64dbg / WinDbg / gdb / Frida / LLDB / unicorn / QEMU；Android 侧 jadx / apktool / JEB。工具名即可，参数按现场拼。

## 判据：改对了没有

- 有效：行为差异只出现在目标判断点（授权分支），其他功能照常——这才是精准补丁。
- 反幻觉：字符串命中不等于校验点（"Invalid License" 可能只是文案）；patch 后崩溃多半是偏移落在指令中间；hook 返回 `true` 后解锁只证明这个点被调用过。
- 同一逻辑可能在多处各有一份（启动校验、功能内二次校验、服务端），改完要确认运行时走的是改过那条。
- **换路**：壳/混淆脱不动、或校验在服务端时，本地改动没有产出，转动态观测或把卡点上报。

## 交付清单

Hash 与元信息 · 关键函数地址/偏移 · 恢复的算法/协议/结构 · 等价实现 · 复现与验证步骤 · 支撑结论的证据（hexdump、反编译片段、运行回显）。

## 缺样本时

要三样东西：样本本身（或哈希 + 格式 + 架构）、目标行为描述（哪一步不对）、可复现的输入。缺了只能给通用方法，给不出结论。

## 与其他技能配合

- **+ exploit**：漏洞定位 → 利用开发
- **+ malware**：样本分析 → 行为理解
- **+ game-hack**：引擎结构 → 内存修改
- **+ license-security**：授权验证 → 绕过实现
